## 一、为什么需要有限状态机

想象一个场景：你在做一个 JD（职位描述）治理系统，一条任务从浏览器插件上报到入库，要经历这些环节：

```
待处理 → 采集中 → 清洗降噪 → 图谱入库成功
```

但真实世界没有这么顺利，中间会冒出各种岔路：

- 采集失败怎么办？→ 任务失败
- 清洗时发现噪声太多怎么办？→ 任务失败
- 失败后能不能重试？→ 重试回到待处理
- 某个状态下，能不能随便触发别的动作？→ 不能，得受约束

如果纯用 `if-else` 硬写，逻辑会散落在各个函数里，越写越乱，加一个新状态要改十几处。

**有限状态机把这件事标准化了**：明确列出「有哪些状态」「有哪些事件」「每个状态下遇到什么事件跳到哪里」，逻辑一下子变清晰。

> 一句话：**FSM 就是用「状态 + 事件 + 跳转表」把散落的流程逻辑收拢到一个地方。**

---

## 二、FSM 三要素

一个有限状态机，永远只由三样东西组成：

| 要素 | 说明 | 例子 |
| --- | --- | --- |
| **状态（State）** | 系统在某一刻处于什么阶段 | 待处理、采集中、图谱入库成功 |
| **事件（Event）** | 触发状态变化的动作 | 开始执行、获取文本成功、重试任务 |
| **跳转（Transition）** | 在某个状态下，遇到某事件跳到哪个状态 | 采集中 + 获取文本成功 → 清洗降噪 |

**FSM 的本质**：系统永远只处于「有限个状态」中的一个，事件驱动它从一个状态跳到另一个状态。

```
       开始执行          获取文本成功       清洗校验通过
待处理 ────────► 采集中 ─────────► 清洗降噪 ─────────► 图谱入库成功
   ▲              │                │
   │              │ 获取文本失败    │ 数据噪声过多
   │              ▼                ▼
   └─────────── 任务失败 ◄──────────┘
        (重试任务)
```

## 三、跳转表：FSM 的灵魂

FSM 实现里最值钱的设计，就是这张**跳转表**。它用字典把「状态 → 事件 → 目标状态」的映射一次性写清楚：

```python
self.transition_map = {
    self.STATE_PENDING: {
        "开始执行": self.STATE_FETCHING
    },
    self.STATE_FETCHING: {
        "获取文本成功": self.STATE_CLEAN,
        "获取文本失败": self.STATE_FAIL
    },
    self.STATE_CLEAN: {
        "清洗校验通过": self.STATE_SUCCESS,
        "数据噪声过多": self.STATE_FAIL
    },
    self.STATE_SUCCESS: {},
    self.STATE_FAIL: {
        "重试任务": self.STATE_PENDING
    }
}
```

**看这张表你能立刻读懂整个业务流程**，不用去翻几十行代码。这就是跳转表的价值：

- 状态之间的合法流转**一目了然**；
- 加新状态/新事件，**只改这一张表**；
- 非法跳转（比如「清洗降噪」状态下触发「开始执行」）**天然被拒绝**。

## 四、完整实现

```python
# 有限状态机 FSM
class JdTaskFSM:
    # 定义所有状态
    STATE_PENDING = "待处理"
    STATE_FETCHING = "采集中"
    STATE_CLEAN = "清洗降噪"
    STATE_SUCCESS = "图谱入库成功"
    STATE_FAIL = "任务失败"

    def __init__(self, task_id, jd_url):
        self.task_id = task_id
        self.jd_url = jd_url
        # 初始状态
        self.current_state = self.STATE_PENDING

        # 跳转表: {当前状态: {触发事件: 目标状态}}
        self.transition_map = {
            self.STATE_PENDING: {
                "开始执行": self.STATE_FETCHING
            },
            self.STATE_FETCHING: {
                "获取文本成功": self.STATE_CLEAN,
                "获取文本失败": self.STATE_FAIL
            },
            self.STATE_CLEAN: {
                "清洗校验通过": self.STATE_SUCCESS,
                "数据噪声过多": self.STATE_FAIL
            },
            self.STATE_SUCCESS: {},
            self.STATE_FAIL: {
                "重试任务": self.STATE_PENDING
            }
        }

    def trigger(self, event):
        """触发事件, 尝试状态跳转, 返回是否跳转成功"""
        state_rules = self.transition_map.get(self.current_state, {})
        if event not in state_rules:
            print(f"[任务{self.task_id}] 当前【{self.current_state}】不能执行事件:{event}")
            return False

        old_state = self.current_state
        self.current_state = state_rules[event]
        print(f"[任务{self.task_id}] {old_state} --【{event}】--> {self.current_state}")
        return True


if __name__ == "__main__":
    # 模拟一条从浏览器插件上报过来的JD治理任务
    task = JdTaskFSM("T001", "https://xxx.zhipin.com/job/xxxx")
    task.trigger("开始执行")
    task.trigger("获取文本成功")
    task.trigger("清洗校验通过")

    print("\n=== 模拟失败重试流程 ===")
    task2 = JdTaskFSM("T002", "https://xxx.lagou.com/job/yyy")
    task2.trigger("开始执行")
    task2.trigger("获取文本失败")
    task2.trigger("重试任务")
    task2.trigger("开始执行")
    task2.trigger("获取文本成功")
    task2.trigger("清洗校验通过")
```

**核心理解**：

- `trigger(event)` 只做一件事：查当前状态的规则表，看这个事件是否合法，合法就跳转，不合法就拒绝并返回 `False`。
- 状态用**字符串常量**定义，语义清晰、不易拼错。
- 所有跳转规则集中在 `transition_map`，业务逻辑一眼看穿。

## 五、FSM vs 一堆 if-else

这是面试和实际开发里最常被问到的问题：

| 维度 | 一堆 if-else | 有限状态机 |
| --- | --- | --- |
| 逻辑位置 | 散落在各处，难找 | 集中在跳转表 |
| 加新状态 | 改多处代码，易漏 | 只改跳转表一处 |
| 非法流转 | 容易漏判 | 天然被拒绝 |
| 可读性 | 越写越绕 | 状态图即文档 |
| 适用规模 | 状态少（2~3 个） | 状态多、流转复杂 |

> 经验法则：**状态超过 3 个、流转开始分岔，就值得上 FSM**。低于 3 个用 if-else 反而更简单，别过度设计。

## 六、适用场景

| 场景 | 怎么用 FSM |
| --- | --- |
| **订单状态** | 待支付 → 已支付 → 已发货 → 已完成（+ 退款/取消岔路） |
| **任务治理** | 采集 → 清洗 → 入库，支持失败重试 |
| **网络连接** | CLOSED / LISTEN / SYN_SENT / ESTABLISHED |
| **游戏角色** | 待机 / 行走 / 攻击 / 死亡，各状态间有限切换 |
| **对话机器人** | 意图识别 → 槽位填充 → 确认 → 执行 |

> 判断标准：**你的业务是不是「有限个阶段 + 事件驱动流转」？** 是，就适合 FSM。

## 七、FSM 速查表

| 点 | 要点 |
| --- | --- |
| 本质 | 状态 + 事件 + 跳转 |
| 核心价值 | 把复杂条件判断梳理成清晰状态流转 |
| 灵魂 | 跳转表 transition_map |
| 三要素 | State / Event / Transition |
| 非法跳转 | 跳转表查不到即拒绝 |
| 何时用 | 状态多、流转复杂（>3 个状态） |
| 何时不用 | 状态少，if-else 更简单 |

---

**一句话总结**：有限状态机用「状态 + 事件 + 跳转表」把散落的条件判断收拢成一张清晰的状态流转图，状态越多、分岔越复杂，它的价值越大，是治理复杂业务流程的利器。
